# Usefulness pilot after technical acceptance

Use explicitly approved or synthetic tasks from two projects and several volunteers
with all three coding tools. Complete native client/security acceptance first.
Compare matched task types under: existing project documentation, an intentionally
maintained static runbook, and the runbook plus selected dynamic learnings. Use the
same model/tool settings where possible and independent held-out cases. Knowledge
created from a test case is not an independent success on that same case.

A human reviewer records correctness, necessary corrections, known pitfalls avoided,
search/context overhead, reviewer effort and total task effort. Record actual token
or provider cost only where available; no fabricated savings. Aggregate team-level
results, not hidden employee rankings or productivity surveillance.

Stop or revise the feature if review effort or irrelevant suggestions outweigh
avoided errors. Prefer the static runbook when it performs as well at lower cost.
The number of stored learnings and number of tool reads are not success metrics.
